# 16 October 2026

## Work registry: one mission id across prompts, sessions and runtimes

Frank asked how every prompt, chat and cloud session gets registered in GitHub
automatically, lands on the right runtime and machine, rolls into one queue
against the estate objectives, and stays observable from inside a cloud session.
This slice surveyed the estate and wrote the plan; it wired nothing live.

`docs/WORK-REGISTRY.md` records the decision: GitHub Issues plus one Project v2
are the registry, a mission id (`M-YYYYMMDD-xxxxxx`) is the join key every
branch, PR, CCR session title, routine run, queue item and receipt carries,
prompts are captured locally into `~/.starlight/missions/` and never committed,
and this hub reconciles on the `fleet-watch` cadence into one sticky digest issue.

Survey result: eight of nine primitives exist (ops ledger and `/ops-sweep`,
machine queues and pulse heartbeats, `queue_reconcile.py`, `mission_envelope.py`,
SIS run receipt v1, `fleet-watch`/`estate-ci-watch`, merge steward, routine
contract and digest, `/dispatch` audit log, `starlight-memory`, spec-trace daemon
behind `tailscale serve`). Missing: the join key, prompt-boundary capture, a
cross-runtime session index, the Project (SIS `PROJECT_BOARD_SPEC.md` was never
applied), and an explicit objective binding beyond `clone-manifest.json`
`production_targets`.

Three Starlight pieces to build: `packs/mission-ledger` in `claude-skills-library`
(SessionStart / UserPromptSubmit / Stop hooks plus a `starlight mission` CLI),
`scripts/session_index.py` and `scripts/project_sync.py` here under a new
`work-registry.yml`, and one six-hour CCR observer routine obeying the routine
contract. Six phases; phase 3 needs one `project`-scoped token in a hub
environment restricted to `main`. No local worker starts, so the c940 RAM HOLD
does not block phases 0 to 2. Queen activation (Ops234) is not a dependency.
