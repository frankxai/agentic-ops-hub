### Routing and switching contract

Tenant controls: outcome/profile; automatic or pinned role models; permitted providers/harnesses; managed or customer-key payer; region/privacy requirements; quality floor; maximum run/period spend; permitted provider/model/harness fallback; and experiment mode (frozen, recommend, or adapt within policy). Defaults are recommendations and cannot override an explicit tenant restriction. A project or user override can narrow platform/tenant permissions; it cannot widen them.

Routing order:

1. Authenticate user and derive account/project scope server-side. Resolve platform, tenant and project restrictions into one effective policy.
2. Discover licensed/entitled routes and the applicable credentials; intersect catalog availability with recent endpoint health and tested harness capabilities. Catalog listing, installed binary, access and demonstrated compatibility are different evidence.
3. Compile a task plan and versioned context packet. Filter required modalities, tools, schema behavior, context/output bounds, privacy, approved source rights and maximum cost.
4. Apply an explicit user pin if eligible. Otherwise rank approved candidates by task quality, creator repair effort, reliability, latency and full outcome cost. Operational health can temporarily remove an endpoint; it cannot waive restrictions.
5. Reserve a bounded budget, pin the foundation and route policy for the run, then execute through the selected adapter. Emit route reason and actual endpoint/model/payer receipts.
6. At a safe boundary, process a fallback or requested switch. Keep accepted artifacts and portable task/tool receipts; construct fresh target-model context. Do not transplant hidden reasoning, provider signatures or opaque session state.

Provider fallback changes an approved endpoint while preserving the model where possible. Model fallback creates a labeled new attempt using the approved candidate chain and the remaining budget. Harness fallback requires a tested state/permission/tool adapter; it is not an interchangeable drop-down for arbitrary in-flight agents. Strict model pinning waits or pauses if no permitted route exists. BYOK never silently changes to Arcanea-funded access. A policy rejection, exhausted budget or content restriction is not an invitation to bypass the restriction through another model.

Use a common capability declaration for each adapter (protocol/version, tool schemas, JSON guarantees, multimodal inputs, workspace isolation, cancellation, checkpoint/resume, streaming and trace/cost support). Unknown or unsupported required capabilities fail eligibility. Provider-specific reasoning/temperature options are compiled by the adapter, not blindly copied between families. Support switching before a run and between planned steps; mid-stream switching preserves the partial draft and starts a visible new attempt.

Both gateways expose provider controls: [Vercel provider options](https://vercel.com/docs/ai-gateway/models-and-providers/provider-options) and [model fallbacks](https://vercel.com/docs/ai-gateway/models-and-providers/model-fallbacks); [OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) exposes allowlists, fallback controls, parameter support, privacy and price limits. Compile only the approved subset of candidates into those settings. Gateway failure routing does not measure narrative quality or enforce the complete Arcanea budget/approval policy.

### Versioned foundations and isolated tenant learning

An agent foundation is an immutable versioned bundle of role instructions, approved skills/tools and schema versions, retrieval/context policy, memory policy, model-route policy, workflow behavior and evaluation references. It is separate from the user's manuscript/canon data. A tenant deployment points to a stable foundation, an optional candidate and a prior rollback version. Receipts retain source hashes and all relevant revisions.

Tenant-specific approved preferences and knowledge are scoped private overlays. Preserve the source, confidence and approval of each preference/fact. A creator accepting a scene is evidence for that context, not permission to overwrite their general style or canon. Do not train on, export, distill or share private work between tenants without the required consent and provider/IP permissions. Global improvements use approved synthetic/public/licensed fixtures or separately consented material. Base model weights do not improve merely because prompts and memory change; fine-tuning is a separate supported, rights-cleared training and evaluation process.

Each customer-controlled experiment has: tenant/project and allowed data; baseline/candidate foundation hashes; a specific hypothesis; permitted model/harness candidates; independent spend and concurrency caps; frozen evaluator/hold-out revisions; outcome metrics and stopping rule; approved promotion scope; expiration and rollback. Platform-funded evaluation is accounted separately; ordinary user credits do not silently fund exploration. Tenant consent is recorded and can be revoked for future experiments.

Use events such as a failed run, repeated repair, a newly available model or explicit creator feedback to propose bounded experiments. Avoid perpetual recursive improvement jobs. Change one material factor at a time initially, repeat nondeterministic samples, compare under equal total budgets, and hold the evaluation rules outside the candidate agent's write scope. Model-based judgment needs independent-family review and creator calibration. Low-sample or conflicting evidence stays inconclusive.

Promotion flow: observed problem -> candidate branch -> sandbox evaluation -> private shadow comparison -> eligible new-job canary -> measured promotion or rejection -> monitored stable version. Shadow runs have explicit spend/data authority and never replace user-visible drafts or invoke production side-effect tools. Canary means an opted-in project/new run using a candidate; active runs keep their foundation version. Promotion uses a conditional version update and an audit receipt, so concurrent changes cannot overwrite each other. Rollback changes future routing/foundation pointers; it does not erase accepted user artifacts.

### Production autonomy boundaries

| Change | Default authority |
|---|---|
| Known safe retry with backoff, circuit breaker, checkpoint recovery | Automatic within existing budget/permission policy |
| Move to a pre-approved endpoint/model after an eligible failure | Automatic only if the tenant enabled that fallback |
| Draft a new prompt/retrieval/skill/route candidate | Budgeted isolated experiment |
| Promote a validated tenant configuration | Recommendation by default; automatic only within the tenant's pre-authorized adaptation scope |
| Promote world facts, overwrite accepted prose, publish | Existing creator/Publishing House approval |
| Change shared code, schemas, permissions, secrets or billing rules | Patch/PR, required independent review and the applicable release authority |

Recovery should use deterministic checks and bounded controllers where possible. Agents can diagnose failures and propose repairs; they cannot grant themselves new tools, alter evaluators, expand quotas or approve their own platform release. Unknown provider outcomes remain held for reconciliation. Failed/rejected versions stay in the evidence history. The user can freeze adaptation, view the change reason, return to the prior version, stop a job and recover their work.
