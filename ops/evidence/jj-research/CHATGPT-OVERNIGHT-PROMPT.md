THE PROBLEM

Many AI coding agents (from several providers) now work in parallel on the same repositories. Today the coordination is branch-per-agent, git worktrees, a path-claim ledger (an agent claims the file globs it will write, with a time limit, and a second agent claiming an overlapping glob is refused), and a merge gate where the agent that authored a change cannot be the one that approves it. This works, but it costs disk, it does not stop patches that each pass alone from failing when combined, and it gives no reliable record of which agent changed what.

Jujutsu (jj, a Git-compatible version control system originally by Martin von Zweigbergk at Google) looks like a better substrate: the working copy is a commit, conflicts are stored as data instead of blocking you, every operation is in an undoable operation log, and workspaces share one store so they cost far less than worktrees. A third-party npm package, agentic-jujutsu (author ruvnet, MIT, version 2.3.6, last published 2025-11-24), wraps jj with a self-learning layer. I assessed it and decided not to use it. Facts I verified: its own README states that its ML-DSA signatures, SHA3-512 fingerprints and HQC-128 encryption are placeholders, with real cryptography promised for a 2.4.0 that was never published; all 15 of its versions were published within 14 days, 12 of them on 2025-11-10; its claims of "23x faster than Git" and "87% automatic conflict resolution" are the author's own and I found no independent benchmark. A stronger reference exists: the GitHub repository CodeAlive-AI/jj-agentic-workflow (a methodology with guarded wrappers, hooks and a hazard test suite; no licence shown, so read it for ideas and copy no code). Its README lists hazards of running jj with several writers: jj undo and jj op restore rewind the whole repository view and silently revert other workspaces; even jj status snapshots the working copy and absorbs stray files; there is no untracked state, so a secret written to disk is committed the moment any jj command runs and stays readable in jj evolog; deleting a Git ref with default config silently abandons commits; a revset that matches nothing returns empty instead of an error.

MY THESIS, WHICH YOU MUST TRY TO BREAK

Parallel-agent version control has two problems. The mechanical one (locks, textual conflicts, workspace cost) is mostly solved by plain jj once its hazards are guarded. The semantic one is not solved by anyone: changes that are textually clean but break each other, work lost to a wrong command, secrets captured by auto-snapshot, and no provenance. A layer built on jj that adds a guarded command surface, path and symbol claims, an integrate-then-test gate, signed receipts bound to real operations, and measured trajectory memory could beat plain worktrees, plain jj, and the existing agent-workflow projects. Your job is to find out whether that is true, to build the parts that survive, and to say plainly what does not. A well-evidenced result that disproves the thesis is a first-class deliverable and is worth more than a flattering one.

PHASES (time-box each; write PROGRESS.md at the end of every phase with what is done, what is next, and what you now doubt)

Phase 0, about 30 minutes: attack this brief. Read it as an adversary. List the five most likely ways the thesis or the plan is wrong, what you would check first for each, and anything in this prompt that is false or unsupported. Write RED-TEAM-OF-PLAN.md. Change your plan accordingly before you proceed.

Phase 1, about 2 hours: research. Produce DOSSIER.md with one entry per source: claim, URL, date read, confidence, what we should adopt, what we should beat, what we should reject. Finish with a ranked list of the techniques most likely to move the semantic problem, and a kill list of ideas not worth pursuing. Use parallel sub-tasks or parallel searches for independent clusters (references, alternatives, papers, vendor features), then reconcile contradictions yourself.

Phase 2, about 2 hours: reproduce hazards on a current jj release you install in the sandbox. Write a test suite where every hazard test fails without a guard and passes with it, so a test that cannot fail is caught. Cover the five hazards above, and test one I have not seen documented: jj snapshots do not run Git hooks, so a secret scanner installed as a Git pre-commit hook would never see a secret that jj commits. Prove or refute it. Also test: what jj does when two workspaces edit the same file, what jj evolog exposes after a file is deleted, how colocated mode interacts with Git hooks and with git commands run in the same directory, and what a concurrent jj command does to a second workspace mid-operation.

Phase 3, about 3 hours, the largest block: build, in this order of leverage, each layer behind a gate you define in writing before you write the code, and stop at the first layer whose gate fails: (1) a guarded jj command surface that blocks the destructive and hook-bypassing cases, scans for secrets before any snapshot, turns empty revsets into errors, and refuses ref deletion that abandons commits; (2) agent workspaces, one per agent, with a path-claim step before the workspace is writable and a bookmark naming scheme so the result looks like a normal branch to a Git merge gate; (3) receipts bound to reality: extend the signed-receipt scheme so it covers a real operation id from the operation store and a per-agent identity, with tests where the wrong operation or wrong agent fails; (4) the semantic gate: construct the combined result of every live agent head (jj new with several parents), run the repository's tests on it, and report the passes-alone-fails-together rate; add symbol-level claims, not only path claims, and test whether they reduce that rate; (5) the trajectory-memory measurement harness: same tasks with retrieval of past graded trajectories switched on versus off, graded by a model from a different provider than the maker, with enough tasks and repeats that you can state whether the difference is real, and a plain statement if it is not; (6) provenance: record which agent and model wrote each change in commit trailers and show it survives a rebase and a squash. If 1 to 4 pass, sketch (not build) a pilot where conflicts in a canon of world-building documents are kept as first-class objects for a human curator.

Phase 4, about 1.5 hours: honest comparison on identical tasks and one machine class: plain Git worktrees, plain jj workspaces, jj with your layer, and GitButler if it installs in your sandbox. In your own disposable sandbox only, you may also install agentic-jujutsu 2.3.6 to test its published claims (the 23x and 87% figures) with a reproducible benchmark; never run it against anything real. Metrics: lost-work incidents, passes-alone-fails-together rate, merge time, peak memory, disk use, secrets caught. Report negative results next to positive ones, with the raw logs.

Phase 5, about 1 hour: adversarial pass and handoff. Attack your own deliverables as a skeptical maintainer who has already declined to adopt them; fix what you find or record it as an open defect. Write FINAL-REPORT.md and NEXT-SESSION-PROMPT.md, a prompt that would let another agent with no memory of tonight continue the work.

HOW TO MAX OUT THE SESSION

Decompose into parallel streams wherever tasks are independent (literature clusters, hazard tests, benchmark design) and reconcile them before moving on. Write a hypothesis and the result that would falsify it before every experiment, then run it and record the outcome even when it embarrasses the hypothesis. Prefer a small experiment that runs now over a large design that does not. Check your own reasoning: after each phase, list what you inferred without checking and go check the most consequential of them. Where two reasonable designs exist, build or at least prototype both and compare. Keep a running log of dead ends; they are findings. Do not spend the night on formatting. Spend it on evidence.
