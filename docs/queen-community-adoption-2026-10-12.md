# Queen community adoption brief

Prepared 12 October 2026. This is a proposed adoption path connected to the [continuation packet](queen-continuation-2026-10-12.md), [existing product decision](QUEEN-PURPOSE-AND-PRODUCT.md) and [foundation map](QUEEN-FOUNDATIONS-AND-NEXT-GOALS.md). A public installation package and independent adopter success have not been established by this slice. Source component acceptance remains **MERGED_NOT_LIVE**.

## First adopter and useful job

Begin with a solo builder or small team already using a supported native coding harness. Their job is to leave one selected issue-bound task, return to an inspectable artifact, understand any hold and continue after interruption without losing work or repeating a costly action.

The first exercise should create a source-linked repository investigation with a concrete recommendation and evidence the operator can use. Choose an actual admitted issue, with bounded inputs and read-only scope. Independently inspect the output against the same inputs. A dashboard animation, process census or generated status report alone cannot satisfy the exercise.

Use manual native continuation as the comparison: same issue, repository snapshot, artifact expectations, time/cost limits and recovery event. Measure accepted output, elapsed time, operator interventions, rework, resource use and actual cost. A claim of superiority needs this comparison; an expanded roster or model name cannot provide it.

## What an adopter should receive

| Deliverable | Acceptance for the first release candidate |
|---|---|
| Portable implementation | Versioned public source/package with reviewed license/dependencies; the exercise requires no private Ops source or credentials |
| Supported harness matrix | Exact tested versions and explicit observe/checkpoint/continue/steer/interrupt/compact/close capabilities; unsupported actions stay visible |
| Guided local setup | Configurable workspace/state paths; existing user-owned credentials; safe defaults and no Frank-specific machine assumptions |
| Inspect and dry run | Show intended session/repo/owner/permissions/budget and holds before native writes; no fabricated success or dispatch |
| Useful task example | Sample issue, reproducible inputs, expected useful artifact and an independent acceptance rubric |
| Recovery demonstration | Acknowledged interrupt, preserved checkpoint/output, controlled restart and uncertain-submission reconciliation |
| Operator controls | Pause, deadline, budget, permission boundary and supported stop; actual owned-runtime close distinct from turn interruption |
| Honest status interface | Installed, observed, owned, executing, held and accepted states with source age and next action |
| Diagnostics and rollback | Redacted support bundle, failed dependency guidance, retained work, documented uninstall without deleting native histories |
| Contributor workflow | Existing issue tracking, scoped PRs, fixtures, exact-revision review and release compatibility policy |

These are release requirements, not descriptions of an existing installer. Reconcile the reviewed Registry before selecting public source placement. Ops owns private runtime operations, config owns executable profiles, the hub owns sanitized guides, SIS owns agreed portable intelligence contracts and skills owns reusable operator guidance. Preserve their accepted boundaries. Do not create another platform or copy private code into public repositories without license/security review.

## Privacy and authority

Raw founder prompts, provider keys, session transcripts, personal domain data and private operational evidence stay in their original private stores. The public exercise uses sanitized inputs and opt-in diagnostic sharing. Telemetry, if added, needs a documented data contract and operator choice.

An adopter's Queen must have authority only over explicitly enrolled sessions and named workspaces. Ownership needs authentication and real host enforcement, independent of model text. Retrieved history, tools, worker messages and support bundles remain untrusted data. They cannot grant permissions, change budgets or declare a result accepted.

Default to one local admitted task. Show unavailable capabilities and offline/unknown state. Keep model context handling, knowledge curation, RAM release and storage cleanup distinct. Cleanup requires exact owned resources; native histories, dirty work and writer locks remain preserved. The private prompt archive in this conversation is authorized local preservation, not a default bulk-ingestion feature for adopters.

## Delivery order and success criteria

1. Prove the local useful-task pilot in the existing programme. Actual host boundaries, native identity, stop/recovery and independent artifact acceptance must pass. Record failures and real cost. Public packaging cannot repair an unproved execution loop.
2. Prepare a public release candidate in the accepted repository. Include the implementation, example, bounded permissions, version matrix, license notices, install/inspect/run/recover/rollback instructions and redaction contract. Test from a clean state, without founder-specific profiles or private source.
3. Rehearse the exact candidate with an independent operator. The existing foundation guide proposes reproduction within 60 minutes after publication; use a prepublication rehearsal to find defects, then record the actual later adopter result. Report elapsed time, setup failures, artifact acceptance and recovery. Missing access or a failed artifact keeps this gate open.
4. Refine instructions and implementation from observed friction. A confusing hold, wrong path, duplicate prompt, authentication failure or lost checkpoint becomes a regression case. Retain failed attempts and clarify what changed.
5. Complete exact-revision independent engineering/security review and applicable design/accessibility review. Publish only through the authorized release path. A merged guide or synthetic rehearsal cannot establish live adoption.
6. Run the existing two-week pilot scoreboard before expanding scope. The prior foundation proposal calls for 20 issue-bound tasks, at least 90% acceptance, complete evidence/cost coverage for accepted work and zero unauthorized external actions. These are proposed targets, not achieved results. Reconcile current budget authority rather than inferring new paid allowance from this brief.

A release is useful when an operator can independently install, complete, inspect and recover the chosen task, then decide whether Queen saves effort compared with native continuation. Record who performed the exercise, the exact version, environment, input, artifact digest, acceptance, elapsed time, recovery event and remaining defects. Collect this evidence privately; share a sanitized receipt with consent.

## Interface quality

Keep the existing product and visual direction. Use sentence case, clear typography, accessible contrast, keyboard focus, reduced motion and responsive layouts. The home screen should answer: what is being done, whose task is it, how fresh is the evidence, what is held, and what happens next.

Live motion must follow a real state change or serve a deliberate decorative purpose. The terminal's existing optional foreground star twinkle is separate from the broader cinematic interface goal. Measure CPU/RAM/paint behavior in the actual surface, pause unnecessary work when hidden and respect reduced motion. New visual generation needs the established provenance/taste records. Native desktop/mobile inspection and interrupted-transition checks remain release evidence.

## Community participation without an extra queue

Use the existing owning issue and repository contribution flow. Good contributions include one reproducible recovery defect, one independently accepted task example, a documented native harness compatibility result or a measured setup improvement. Each names an owner, exact inputs, output and acceptance. Avoid distributing tasks merely to occupy agents.

Start participation through prepared documentation and opt-in rehearsal invitations under the existing community owner. No message, campaign, community post or release was sent by this preservation task. Demand, pricing and paid-service claims need separate evidence and the relevant publication gates.
