Status: adoption guidance and a bounded operating proposal. This document activates no agent, schedule, credential, paid route or merge permission. Keep the [existing merge steward](MERGE-STEWARD.md) and its [rollout gates](MERGE-STEWARD-ROLLOUT.md).

## Ownership and personalities

Resolve portfolio authority from reviewed `agentic-ops/registry`, including exclusions, repository ownership, artifact placement and architecture decision IDs. Executable Queen profiles belong in `starlight-agent-config/core/agents/starlight-queen`; this Hub supplies sanitized adoption guidance. Provider sessions are delegated workers. They do not become canonical identities.

Existing proposed rosters must be reconciled with accepted configuration before installation. A role name, prompt or successful workflow run proves neither identity admission nor runtime enforcement.

Use one coordinator and task-specific roles. A personality defines judgement, voice and responsibilities; a permission boundary defines what that role can actually do.

| Role | Useful responsibility | Required output |
| --- | --- | --- |
| CEO | Rank explicit founder intent, customer value and dependencies within current WIP limits | One chosen outcome, owner, stop rule and preserved alternatives |
| CMO | Identify the user's job, evidence, promise and activation path | Source-backed copy and measurable funnel hypothesis |
| CTO | Choose maintainable implementation and resolve integration risks | Failure/recovery plan, exact tests and rollback |
| CAIO | Choose an evaluated model route and control inference spend | Task-specific quality, latency and cost comparison |
| Design director | Own typography, hierarchy, brand assets, interaction and responsive behaviour | Before/after evidence, mobile/keyboard/reduced-motion review |
| Repository steward | Recover original task intent and reconcile its branch, issue and owner | Current next gate and exclusive file scope |
| Maker | Produce the accepted slice in an isolated lane | Actual artifact and revision-bound verification |
| Independent checker | Challenge implementation and claims on the exact revision | Coverage, findings and explicit unresolved gaps |
| GitOps integrator | Recheck review, protection, ownership and deployment ordering | Normal merge receipt and receiving-main verification |

These are responsibilities to map onto existing admitted agents, not a request to start nine processes. The maker cannot supply its own independent acceptance. A classifier has no merge authority.

## Model and tool routing

Start with deterministic Git/API checks. Use a small model for bounded interpretation, then escalate only where the task requires it. Compare routes on the same accepted-output task; a model name or provider benchmark does not establish portfolio superiority.

| Work | Candidate route | Boundary |
| --- | --- | --- |
| Inventory, head/check comparison, duplicates and caps | Native CLI and rules | Head equality is not proof of supersession or safe deletion |
| Intent summaries, labels and routine drafting | Haiku 5.5, or an actually available Luna route | No approvals, secret access or merge authority; benchmark sampled decisions |
| Bounded implementation and tests | Available Codex Cloud or another admitted remote worker | Pin source and environment; return a full patch and actual commands |
| Architecture, recovery, complex source review | Capable Sol/Astra/Sonnet/Opus route supported by the actual harness | Independent checker and bounded rounds; preserve contrary findings |
| Visual alternatives and interactive refinement | v0 with the accepted brand/component system | Separate design exploration from production integration |
| Repository integration, CI repair, native app/CLI work | Native repository tools | v0 cannot replace these verification steps |

As checked on 13 October 2026, [v0's ChatGPT integration](https://v0.app/docs/chatgpt) lists GPT-6 Astra, GPT-5.6 Sol/Luna and GPT-5.5 variants. It does not list GPT-6.1 Sol. The installed MCP message method separately accepts only `v0-mini`, `v0-pro`, `v0-max` and `v0-max-fast`. Verify interface support and the active payer before dispatch; never translate a local model setting into a claim about Cloud or v0 execution.

Haiku 5.5 is a candidate for inexpensive classification: [published pricing](https://platform.claude.com/docs/en/about-claude/pricing) is $0.10 input/$0.50 output per million tokens for prompts up to 100K tokens, with a higher tier beyond that. A hypothetical 718-item pass at 8K input and 1K output per item is about $0.93 before retries, tools, caching, tax or review. This is a scenario, not a paid run or measured accuracy. Test ten representative cases first, including hostile PR text, missing intent, stale review, incomplete metadata and conflicting ownership. Never use a cheap model to waive a protected gate.

Use v0 for focused visual comparisons, reusable responsive components and design-mode refinement when the visual feedback saves work. Use Figma for shared component/variable governance and reusable design source when cross-product collaboration needs it. Native Next.js remains the integration and delivery path. A Figma file is not required for every reversible code change.

## Local and Cloud admission

Cloud can move a repository-contained build off a constrained machine. It does not remove source-access, environment, quota, cost or release requirements. Codex Cloud uses the [account's Codex allowance](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan); inspect actual limits rather than assume unlimited capacity.

Every dispatch packet names original user intent and task/issue reference, canonical repository, immutable base, exact environment, owner, exclusive paths, allowed tools, payer, token/time/retry limits, acceptance, return format and stop condition. Remote workers preserve other work and receive no merge/deploy authority unless explicitly delegated.

Return actual source head/tree, changed paths, full patch, runtime versions, command exit codes, evidence hashes and remaining gaps. Recheck current main and use integration preflight before applying. `READY`, a finished turn and a no-diff task are not accepted customer outcomes. An `ERROR` task receives diagnosis before retry; missing error detail remains unknown.

Local admission follows fresh PP and disk evidence. Below the RAM or disk floors, preserve existing work, avoid new local workers/builds/worktrees and use permitted text/read operations. Never kill a foreign process, remove a writer lock by age or delete a branch to create capacity.

## Routines through the existing controller

Extend the existing controller and merge steward; do not install another orchestration loop. These trigger changes remain proposals until their owner implements and verifies them.

| Trigger | Bounded action | Paid work and stop rule |
| --- | --- | --- |
| PR opened, made ready or new head pushed | Capture head, intent, paths, ownership, dependency and check state | Deterministic first; one interpretation only when inputs changed |
| Required checks reach a terminal state | Re-evaluate the exact head against current policy | No repeated model review for an unchanged, already reviewed head |
| Remote task completes/errors | Validate returned artifacts or record the failure | One coordinator; no blind redispatch |
| Normal merge | Inspect receiving checks, source/deployment binding and relevant smoke tests | Pause the next production-affecting merge on failure |
| Daily cost exception | Compare current/prior fixed windows, retries and unaccepted work | Read-only digest; do not change billing or buy credits |
| Weekly quality review | Inspect accepted output, escaped defects and user feedback | Propose one measured improvement; keep unfinished intent |

Deduplicate on repository, issue/PR, immutable head and policy version. One durable owner holds each task. Use finite retries with backoff, an accountable exception queue, cancellation and a kill switch. A periodic health trigger may collect metadata; it must not invoke a model when nothing consequential changed. Enforce time, tokens, concurrency and budget in the host, not merely in prose.

## PR and branch decisions

Order work by explicit user intent, dependency, impact on the user, acceptance evidence, risk and repair effort. Preserve author descriptions, linked issues, return artifacts and contrary reviews.

1. Preserve drafts and active owners. Ask their owner for the next gate rather than silently making them ready.
2. Repair failed checks and reconcile conflicts in an admitted owner lane.
3. Review clean candidates against full source, actual intent and current accepted main. Green CI proves only its own scope.
4. Bind independent review to the exact head and re-read all required checks, protection, ownership and release authority immediately before normal merge. Never use admin bypass or a fabricated signoff.
5. Integrate one PR at a time; verify receiving main and the relevant product behaviour before the next release change.
6. Recommend closure only with content-level supersession or an explicit abandoned-intent decision. Age, title similarity and absence from the open-PR list are insufficient.
7. Recommend branch cleanup only after verified merged ancestry/content, recoverable source, closed intent and no live/local-only owner. Deletion remains a separate authorized action.

The existing steward's three-tier design, shadow pilot, exact-source guards and rollout acceptance remain in force. Do not turn all targets live because scheduled jobs report success. Confirm actual configured steps, review comments, permission scope, model availability and spend enforcement.

## Quality and success

Customer value is the primary measure: can the intended user finish the job, recover an interruption and export a usable result? Internal metrics are accepted outcomes per dollar, time to accepted integration, rework, escaped defects and founder interventions. Token volume, agent count, commits and merged PR totals are supporting observations.

For a designed surface, require a pinned brand pack, purposeful hierarchy and motion, useful copy, working CTAs, keyboard/focus/touch and reduced-motion paths, realistic empty/loading/error/recovery states, representative mobile/desktop evidence and measured performance. Record accessibility and performance gaps rather than invent scores. Factual claims, rights, pricing, checkout and publication retain their applicable gates.

Suggested pilot acceptance: all ten sampled triage decisions preserve source/intent; zero unsafe merge/close recommendations; every executed merge has exact review and normal protection; no duplicate dispatch; no budget overshoot; at least one actual useful artifact accepted. Expand concurrency or cheaper model coverage only after these pass. Keep forecasts separate from observations.
