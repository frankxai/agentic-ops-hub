# Company swarm lane prompts

TL;DR: Assign independent capability work with specific artifacts, integration seams, adversarial cases and stop conditions; run the responsibilities in admitted waves.

Prepared 11 October 2026. Read the [coordinator](COMPANY-SWARM-COORDINATOR.md) and [programme](COMPANY-SWARM-BUILD-PROGRAMME.md) first. These are sixteen responsibilities, not sixteen simultaneous agents or granted write lanes.

Every prompt inherits the coordinator's compiled assignment: current product/issue/source, verified repo/origin/base/branch, exclusive exact output files, read-only sources, permitted inputs/actions, actual budgets, instructions, useful acceptance and stop condition. Reject unresolved assignments before execution. Preserve others' changes. Use the actual harness and admitted capabilities; model names in old records are not automatic provider permissions.

## S00: Portfolio, customer outcome and economics

Wave W0; prerequisites: none. The coordinator supplies exact repo/file ownership before execution.

```text
Act as the CEO/product analyst for this bounded build. Resolve the accepted portfolio authority and current product owners, then inspect representative code and active issues rather than ranking brands from README marketing. Record the private revenue/subscription baseline separately from a public projection. Produce a candidate outcome map: the exact buyer/operator job, existing sellable artifact, gap between current behavior and delivery, a serious alternative, customer evidence, engineering dependency, owner and next useful action.

Calculate four matched-scope options: existing/free subscription, paid tool plus adapter, adopted software and proprietary build. Break build hours into domain/data, UX, authorization, integration, recovery and review; count maintenance and founder review. Keep subscription-covered inference, API-equivalent tokens and actual new API bills separate. Unknown hours, volume, FX, data price and buying intent stay explicit. Propose a small calibration experiment before a large build. Evaluate delayed revenue work as constrained attention without inventing lost income.

Deliver an owner/source map, staged build/buy/adopt/defer decisions and a private editable cost model. Recommend no more than the currently admitted revenue builds and one shared primitive at a time. Preserve other products and unfinished work. Submit the chosen vertical slice to the coordinator; stop if its owner, inputs or acceptance cannot be resolved. You are read-only in product repos unless separately assigned a lane. Acceptance requires a decision that changes the next engineering action, not a list of fashionable tools.
```

## S01: Admission and assignment compilation

Wave W0; prerequisites: S00. The coordinator supplies exact repo/file ownership before execution.

```text
Compile the selected work into valid assignments using the existing routing, lane and task systems. Inspect current machine/storage posture before spawning workers or starting builds. Verify repo root, origin, exact base, root/deeper guides and separately claimed exclusive paths. An old clean status, JSON digest or another harness's branch does not grant ownership.

Validate every worker assignment has permitted inputs/revisions, actual output paths, current skill/model capabilities, authorized actions, budget/deadline, useful acceptance and a stop condition. Reject self-issued admission/approval tokens and fields supplied by an untrusted caller. Keep the current task ledger authoritative; do not add a parallel task queue or bootstrap every installed MCP. Calculate process multiplication for local stdio dependencies and choose shared or authenticated remote transports where already supported.

Produce a compiled assignment packet with unresolved fields visibly unadmitted, plus a read-only source digest. On HOLD start zero new workers, record the reason and continue permitted preparation. Under admission use the smallest team that has independent work; allocate a distinct verifier and one writer per worktree. Stop at occupied ownership, missing required guide or exceeded resource/spend policy. Acceptance includes deliberate refusal of an unresolved lane and a reproducible valid lane check. This lane defines a proposed admission adapter; implementation cannot claim universal runtime enforcement until exercised.
```

## S02: Shared domain operations and identity

Wave W1; prerequisites: S00, S01. The coordinator supplies exact repo/file ownership before execution.

```text
Inspect existing GenCreator/VIS/SIS operations and entitlement/resource identifiers. Extend the owning domain service with the selected action instead of putting business rules in each UI/MCP tool. Specify stable subject, workspace/brand, resource/version, operation, expected revision, idempotency key, deadline and job/usage references. Keep existing product identity boundaries; sharing an email address is not cross-brand membership.

Implement server-side authentication and resource authorization on every read/write. Validate input at the boundary and derive permission from trusted state. Apply optimistic version checks; use a transaction/outbox where the side effect boundary requires it. Preserve pending/unknown external effects and reconcile before retry. Return observable state and typed conflict/denial/budget/cancellation outcomes. Never expose a service-role credential to the client.

Deliver the operation contract, one working vertical operation, adapter examples and actual positive/negative behavior evidence. A stale edit must preserve the newer edition; unauthorized reads/writes and fabricated client approvals must fail; concurrent duplicates must not create extra local records or trigger a blind duplicate external send. Pass the verified contract to storage, CMS, host and telemetry owners. Stop if identity or catalog authority is unresolved. Acceptance requires observed behavior through at least the selected actual surface, not schema validity alone.
```

## S03: Storage and catalog authority

Wave W1; prerequisites: S02. The coordinator supplies exact repo/file ownership before execution.

```text
Resolve the current VIS source and accepted media fabric before changing data. Explain exactly which system owns asset identity, versions, rights/approval, local index, masters, renditions and placements. Reconcile older SQLite library claims with current Postgres approval/metadata ownership; propose a versioned migration or projection with one truth owner, and never silently dual-write rights.

Extend the accepted storage adapter for the selected private master/preview job. Use opaque stable asset/version keys, deterministic checksums and permitted signed retrieval. Validate media size/type and preserve provenance sidecars and generation ledgers where applicable. A signed URL is a temporary locator, not an approval. Separate private storage from approved public delivery. Retain local originals until an authorized restore acceptance proves recovery.

Deliver one supported asset's ingest/retrieval/restore evidence, a migration/backup/rollback plan and metered storage/request/preview costs. Test interrupted ingest, duplicate bytes, expired/replayed retrieval grants, corrupt download and missing master. Re-indexing must not lose placements or invent rights. Stop on missing right/approval authority, live R2-write/route grant or destructive migration permission. Never claim historical configuration proves current two-device private retrieval. Hand stable IDs and rights query semantics to DAM/CMS; acceptance is verified integrity and permitted recovery, not merely an uploaded object.
```

## S07: Durable workflows and integration recovery

Wave W1; prerequisites: S02. The coordinator supplies exact repo/file ownership before execution.

```text
Map the selected business job across existing workflow owners. Choose one durable owner per job: accepted Cloudflare cross-entity workflow or app-local Vercel workflow where appropriate. A Durable Object holds a justified persistent entity; ordinary business rows remain in their data owner. Use n8n as a bounded internal adapter only when its license and operational fit are understood. Do not introduce a second coordinator or Temporal stack by default.

Implement the useful asynchronous path with durable checkpoints, typed transitions, correlation/idempotency, provider receipt reconciliation, timeouts, cancellation and a bounded retry policy. Separate retryable errors from rejected permission, invalid input and unknown external effect. A canceled job records work and billing already incurred and admits no new provider action. Resume from its real checkpoint; never replay an entire send pipeline blindly.

Deliver a traceable job that completes after a deliberately interrupted worker and exposes accurate status to the user. Test crash before/after a provider effect, duplicate event, expired credential, dead-letter/manual recovery and budget stop. Hand exact status/receipt semantics to the tool and UI owners. Stop on competing ownership or missing side-effect grant. Acceptance requires one observed completed or correctly reconciled interrupted job and a usable recovery route, not an animation or queue diagram.
```

## S08: API, CLI, MCP and host connections

Hand capability truth to the installer and customer-facing docs; do not advertise “all agents can manage everything.”


## S15: Controlled R&D and continuous improvement

Wave W5; prerequisites: S12, S13, S14. The coordinator supplies exact repo/file ownership before execution.

```text
Improve a measured weakness in the existing workflow, skill, prompt, adapter or model route. Select one actual failure or repeated operator/customer pain, with source case, accepted baseline and ownership. Define an improvement hypothesis and budget before modifying anything. Preserve failed/rejected evidence, especially the founder's rejection of simplistic build prompts.

Implement a bounded candidate in an exclusive lane. Use development examples to revise, then separate holdout cases and the serious alternative to assess useful output, factual fidelity, repair minutes, permission/recovery, latency and actual cash. Do not tune against the holdout after seeing its result. Include varied successful and adversarial jobs; unsupported claims or lost work are hard failures, irrespective of lower token cost.

Deliver an inspectable candidate, measured comparison, independent source-bound recommendation and reversible rollout/rollback plan. Promote only under the existing owner/release authority and observe the accepted outcome window. The loop may create a proposed change; it cannot rewrite its own permission policy, self-approve release, start recurring agents or grant new spend. Limit one hypothesis to two refinement rounds before diagnosis. Update existing decision history and compact permitted memory with outcome and confidence. Stop if there is no measured baseline or admitted evaluation budget. Acceptance is demonstrated improvement on the selected useful job without critical regression, not a larger prompt/agent roster.
```
